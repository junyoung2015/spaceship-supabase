## Purpose

This document is the canonical delivery record for v0.1.0. It replaces the
alpha-era roadmap where its assumptions conflict with the current stable
Supabase CLI or with the security requirements of terminal-prompt rendering.
Historical planning documents remain available as historical context; they are
not the product contract for this release.

## Product contract

`spaceship-supabase` is a local, offline Spaceship prompt section. Its default
segment is intentionally narrow:

```text
🔷 abcdefghijklmnopqrst
```

It means that the current working directory is inside a safely identified
Supabase project and the stable Supabase CLI's local linked-project reference
is valid. It does **not** claim a project name, hosted branch, remote status,
or network freshness.

The only supported output formats are:

```zsh
SPACESHIP_SUPABASE_FORMAT="ref"       # default
SPACESHIP_SUPABASE_FORMAT="label+ref" # Production (abcdefghijklmnopqrst)
```

The full 20-character project reference is always retained. Arbitrary
templates, truncation, bare labels, branch-only output, and raw filesystem
interpolation are deliberately unsupported.

Supported visual and behavior settings are:

```zsh
SPACESHIP_SUPABASE_SHOW=true
SPACESHIP_SUPABASE_ASYNC=true
SPACESHIP_SUPABASE_COLOR=cyan
SPACESHIP_SUPABASE_SYMBOL="🔷 "
SPACESHIP_SUPABASE_PREFIX=""
SPACESHIP_SUPABASE_SUFFIX="$SPACESHIP_PROMPT_DEFAULT_SUFFIX"
SPACESHIP_SUPABASE_FORMAT="ref"
SPACESHIP_SUPABASE_SHOW_LOCAL_DB_BRANCH=false
SPACESHIP_SUPABASE_CONFIG_REMOTE=""
SPACESHIP_SUPABASE_USE_LABELS=true
SPACESHIP_SUPABASE_LABEL_FILE="${XDG_STATE_HOME:-$HOME/.local/state}/spaceship-supabase/labels.tsv"
SPACESHIP_SUPABASE_DEBUG=false
```

When explicitly enabled, a valid local database branch is shown only as local
state:

```text
🔷 abcdefghijklmnopqrst (local-db:feature/refactor-42)
```

It must never use `ref@branch`, which would imply a hosted Supabase Branch.

## Stable input contract and precedence

v0.1.0 supports the stable Supabase CLI layout used by the verified v2.72.7
and v2.113.0 fixtures:

```text
<project root>/supabase/config.toml
<project root>/supabase/.temp/project-ref
```

`project-ref` is the live authority and must be exactly 20 lowercase ASCII
letters. The resolver applies this precedence:

1. An explicit `SUPABASE_WORKDIR`, canonicalized relative to `$PWD` when
   necessary. An invalid override renders nothing and never falls back to
   `$PWD`.
2. Otherwise, the nearest safe ancestor containing `supabase/config.toml`,
   walking at most 32 ancestors. A closer boundary stops the search.
3. A valid live `supabase/.temp/project-ref` under that root.
4. Only if no live ref exists, an explicitly selected
   `[remotes.<name>].project_id` mapping where
   `SPACESHIP_SUPABASE_CONFIG_REMOTE=<name>`. Its output carries the mandatory
   `· configured:<name>` marker.

Top-level `project_id` is never treated as a hosted project reference.
`supabase/.branches/_current_branch` is a deprecated local database-branch
file, not hosted branch state. `.supabase/project.json` is a future
unreleased-shell adapter and is not supported in v0.1.0.

## Security and reliability rules

- Prompt rendering is stateless, local-only, read-only, and fresh on every
  render. It does not call Supabase CLI, the network, Node, Python, jq, or read
  credentials.
- All expected path components are regular, non-symlinked entries whose
  canonical locations remain below the selected project root.
- Identity-critical root, config, and project-reference inputs are bounded
  before parsing; malformed, unreadable, control-bearing, multi-line,
  oversized, or unexpected values fail closed without ordinary stderr output.
  The optional local DB branch decoration is independently validated: an unsafe
  branch suppresses only that decoration when an authoritative ref remains
  valid.
- Allowed values are intentionally small: project ref `[a-z]{20}`; local DB
  branch `[A-Za-z0-9][A-Za-z0-9._/-]{0,127}`; config remote
  `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`; label printable ASCII excluding `%`,
  controls, tabs, and newlines, up to 64 characters.
- Filesystem-derived values reach `spaceship::section::v4` only after strict
  allowlist validation. Diagnostics use fixed codes and redact paths and raw
  state by default.

## Explicit configuration and labels

The optional configured mapping is deliberately non-authoritative. For
example, setting `SPACESHIP_SUPABASE_CONFIG_REMOTE=staging` permits only a
valid `project_id` from `[remotes.staging]`, and only when live state is absent.

Labels are manual user-owned decorations, not a persistent identity cache:

```text
spaceship_supabase_label set <safe-label>
spaceship_supabase_label clear
spaceship_supabase_label list
spaceship_supabase_doctor [--verbose]
```

The versioned TSV state is keyed by project ref, created only by explicit
commands, and secured with owner-only directory/file permissions and atomic
writes. A label may decorate a currently resolved ref; it can never select,
resurrect, or replace a project identity. `doctor` is local and read-only.

## Delivery workstreams

### 1. Core safety and UX

- Rebuild the plugin around Zsh-native helpers using `emulate -L zsh`, `REPLY`,
  and an internal context association rather than stdout pipes and value caches.
- Implement safe root resolution, bounded stable-file parsing, live/config
  precedence, opt-in local DB branch decoration, labels, and doctor.
- Remove alpha settings that are inert, misleading, or unsafe: source toggles,
  cache settings, ref prefix/truncation, raw error settings, and unsupported
  output formats.

### 2. Tests, fixtures, and performance

- Replace stale story tests and xtrace coverage gates with behavior-focused
  unit, integration, negative, and security suites.
- Add `tests/run.zsh` as the only local/CI entrypoint. It runs isolated
  `zsh -f` processes with a temporary empty `ZDOTDIR`; `--performance` adds
  the benchmark.
- Use flat tracked synthetic inputs and materialize v2.72.7/v2.113.0 runtime
  layouts in temporary directories. No ignored runtime state or real metadata
  belongs in fixtures.
- Cover freshness, nested roots, strict workdir, malformed and symlinked
  inputs, prompt injection bytes with actual Spaceship v4 rendering, labels,
  permissions, atomic writes, diagnostic redaction, and no-prompt-I/O rules.
- Benchmark five independent 100-render batches on a valid live layout;
  require median P99 below 5 ms and maximum P99 below 15 ms on Ubuntu.

### 3. Documentation and community surface

- Make `README.md` the accurate public hub with text terminal examples,
  verified installation paths, quick verification, privacy guidance, and links
  to configuration, data-source, label, troubleshooting, compatibility, and
  testing references.
- Add `CHANGELOG.md`, `SECURITY.md`, `CONTRIBUTING.md`, `SUPPORT.md`,
  `AGENTS.md`, and `VERSION`.
- Replace copied mobile issue forms and pull-request template with English
  Zsh-plugin forms using only `bug`, `enhancement`, `question`, and
  `documentation` labels.
- Preserve historical documents with clear superseded banners. Mark the
  completed alpha work accurately and add a distinct v0.1.0 release record.

### 4. CI, automation, and supply chain

- Replace partial CI with reusable metadata, lint, secret-scan, cross-platform
  test, benchmark, and release-preflight jobs.
- Use least-privilege permissions, full action-SHA pins, timeouts,
  cancellation concurrency, pinned ShellCheck 0.11.0 for the production plugin,
  and weekly GitHub Actions Dependabot updates.
- Add tag-driven release automation that verifies an annotated, main-reachable
  tag, matching `VERSION`, and curated changelog section before creating exactly
  one GitHub Release.

## Acceptance gates

The release may be exported only after all of these hold:

- renderer behavior, documentation, configuration defaults, tests, and
  changelog agree;
- canonical functional, security, syntax, metadata, and performance gates pass
  from a clean checkout;
- current stable v2.72.7 and v2.113.0 layouts render truthfully and unsupported
  layouts fail silently;
- public-tree audit finds no secrets, absolute developer paths, internal links,
  ignored runtime state, or stale alpha claims;
- public history retains its existing placeholder commit and gains exactly one
  audited `feat: v0.1.0 initial public release` commit;
- public CI is green before the annotated `v0.1.0` tag is pushed;
- repository security/features and protections are enabled where the GitHub
  account permits them; and
- the tag produces one published GitHub Release whose notes match the
  `CHANGELOG.md` v0.1.0 section.

## Public cutover

Implementation and validation occur first on this private release branch. The
public repository receives only an explicit sanitized allowlist: the plugin,
public docs, audited tests/vendors, public `.github` configuration,
`.gitignore`, `.gitattributes`, legal/governance files, `VERSION`, and
`CHANGELOG.md`. Internal planning outputs, developer paths, private repository
references, runtime Supabase state, and historical working artifacts are not
exported.

The existing harmless public placeholder commit is preserved. After the public
tree passes its own tests and secret scan, it receives one ordinary commit:

```text
feat: v0.1.0 initial public release
```

The private repository remains an undeleted historical archive after the public
release is verified.
