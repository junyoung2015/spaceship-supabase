# beta.4 second-tester preparation templates

## Outcome

These templates authorize nobody. The active beta.4 cohort remains the release
owner only unless the user identifies one genuinely independent second tester,
the release owner completes the exact authorization in
[issue #15](https://github.com/junyoung2015/spaceship-supabase/issues/15), and
that person confirms the approved private vulnerability route while signed in.
They provide a bounded, redacted preparation record for that later decision.

1. The only candidate covered by either template is `v0.2.0-beta.4`.
2. Completing a placeholder does not install, test, expand, or authorize
   anything by itself.
3. The release owner alone records a later `go`, `extend`, or `pause` decision.
4. A private beta decision does not authorize stable publication, another tag,
   a branch tip, a third tester, or an external cohort.

## Authorization template

Copy this template only after the user has supplied one independent person and
the release owner is ready to make an exact, separate beta.4 decision. Leave it
unposted while the cohort remains owner-only.

```markdown
## beta.4 second-tester authorization

Status: exact preparation record. This authorization is incomplete until every
required field is completed by the release owner. It does not authorize anyone
until that completion is posted in #15.

| Field | Required value |
| --- | --- |
| Exact candidate | `v0.2.0-beta.4` only |
| Annotated tag object | `834cce75a66c557101be3cdeb7eee9021d585f50` |
| Reviewed implementation commit | `3b3326ff1379e92cfee09ef3285af0722c21e14e` |
| Plugin rollback target | `v0.1.1` |
| Proposed independent second tester | `<identity supplied and confirmed later>` |
| Exact-tag access confirmation | `<can reach the exact tag; public access demonstrates reachability only and does not authorize beta testing>` |
| Approved private vulnerability route | `<signed-in tester confirmed the GitHub advisory form before authorization>` |
| Decision authority | `<release owner>` |
| Evidence window | `<bounded UTC period>` |

1. Scope covers only a detached checkout of the exact beta.4 tag and the
   bounded Core and assigned safe feature rows in the companion evidence
   template.
2. Before installation, the proposed tester independently confirms access to
   the repository's GitHub Security Advisory form while signed in. Suspected
   vulnerabilities go only through that approved private route. Issue #15
   receives redacted status and decision information only.
3. Public issue comments, screenshots, terminal recordings, raw CLI output,
   project refs, project or branch names, paths, configuration, credentials,
   account details, and vulnerability details are excluded from evidence.
4. Sensitive reports remain in the applicable private route for triage and are
   removed afterward where that route permits. Public evidence retains only an
   allowed status and one short sanitized note per section.
5. The release owner alone records `go`, `extend`, or `pause`. A passing matrix
   does not authorize stable publication or a larger cohort.
6. This authorization excludes `main`, branch tips, another tag, a third
   tester, external or phase-2-alpha testing, repository visibility changes,
   hosted-branch work, `VERSION=0.2.0`, a stable tag, and a stable release.
```

## One-person evidence-reply template

Each authorized person uses one separate reply. Use only `pass`, `fail`, `not
run`, or `not applicable`. Each section permits at most one short sanitized
note.

```markdown

Status: inactive until a completed exact beta.4 authorization appears in #15.
This reply does not authorize installation or testing.

| Field | Value |
| --- | --- |
| Candidate | `v0.2.0-beta.4` |
| Tag object | `834cce75a66c557101be3cdeb7eee9021d585f50` |
| Implementation commit | `3b3326ff1379e92cfee09ef3285af0722c21e14e` |
| Role | `owner` or `independent second tester` |
| Allowed results | `pass`, `fail`, `not run`, `not applicable` |
| Sanitized note | At most one short non-security sentence per section |

Do not include account identifiers, project refs, project or branch names,
labels, paths, configuration, raw CLI output, screenshots, recordings, host
information, credentials, or vulnerability details.
```

## Security-route confirmation

The 2026-09-02 release-readiness audit found the repository's GitHub
private-vulnerability-reporting setting enabled. That point-in-time
configuration does not prove that a future tester's signed-in account can
submit a report. The future tester must confirm the advisory form before any
authorization becomes effective.

See the [security policy](../../SECURITY.md) for the public reporting boundary
and [beta testing](../beta-testing.md) for exact-tag installation and rollback.

## Retention and decision boundary

1. Keep only the redacted public status and one sanitized note per section in
   issue #15.
2. Keep sensitive material inside the verified private route for only as long
   as that route's triage and retention policy requires.
3. Do not rewrite older beta authorization or historical evidence comments.
4. Do not use these templates to infer a tester identity, widen access, create
   a release, or mark issue #9 complete.
